# Critique by a

## On b
Objection: The word regex `[^\W_]+(?:['-][^\W_]+)*` swaps the bug it fixes for a new one of the same kind: it breaks ordinary tokens at `.` and `,` into made-up words. "e.g." becomes `e`, `g`. "U.S.A." becomes `u`, `s`, `a`. "10,000" becomes `10`, `000`. "3.14" and "v1.2" become `3`, `14` and `v1`, `2`. Today all of these are single tokens, and fixing them only needs their trailing period removed. Under b, single letters and number fragments enter `word_frequencies`, can rank in `top_words`, and pull `average_word_length` down. That is the same problem as the stray "-" being counted, just with different junk. b lists "3.14 → 3, 14" as an accepted trade-off. It doesn't mention abbreviations or thousands separators, which are much more common in prose.
Grounding: Experiment in a/scratch/crit.py. b's tokenizer on `"3.14 v1.2 e.g. U.S.A. 10,000 $5 C++ #tag"` returned `['3','14','v1','2','e','g','u','s','a','10','000','5','c','tag']`. On the same input, a returned `['3.14','v1.2','e.g','u.s.a','10,000','5','c','tag']`.
Severity: major. It fixes the reported case but adds wrong counts for common inputs.
They do better than me: They split on punctuation between words with no space ("hello—world" and "one,two" become two words each), which mine doesn't. They also normalize the curly apostrophe, so "Don’t" and "don't" count as one word.

## On c
Objection: It uses the same regex as b, so it has the fragmentation problem above. The objection specific to c is that it promises to remove "the whole class of bug" but breaks real Unicode words. `[^\W_]` doesn't match combining marks, so text in decomposed Unicode form (NFD) gets split in the middle of a word. That form is common in text copied from macOS, and in some PDFs and web pages. "naïve" becomes `nai`, `ve` and "résumé" becomes `re`, `sume`. c gives "café works" as evidence, but that was tested only with the precomposed form (NFC). c also matches the curly apostrophe inside words but doesn't normalize it, so `don’t` and `don't` remain two separate words. That leaves the same split-count problem the bug report is about, now for apostrophes.
Grounding: crit.py. c's tokenizer on `unicodedata.normalize("NFD", "café naïve résumé")` returned `['cafe','nai','ve','re','sume']`. On `"it’s don’t"` it returned `['it’s','don’t']`, which differ from the straight-apostrophe `it's`/`don't`.
Severity: major. The reported case is fixed, but the claim of being more correct for all inputs doesn't hold.
They do better than me: Their diagnosis is better. They define what a word is instead of trimming tokens. They found the knock-on effect on `average_word_length`: `"Hello, world!"` gives 6.0 instead of 5.0. They also show that my whitespace boundary leaves `"hello—world"` as one token.

## On my own
Objection: I still split on whitespace, so punctuation between words with no space stays inside the token. The orchestrator's table shows `"hello—world"` → `['hello—world']` and `"one,two"` → `['one,two']`. That is the reported bug ("punctuation attached to words") in a less common spacing. So my claim to fix the cause "for all inputs" is too strong. My fix also strips a trailing combining accent in decomposed (NFD) text: "résumé" → `résume` (crit.py). That is less damage than b and c do to the same text, but it is still wrong. The fix would be to normalize the text to the precomposed form (`unicodedata.normalize("NFC", ...)`) first, and b and c need that step too.
